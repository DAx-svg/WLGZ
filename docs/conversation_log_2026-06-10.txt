================================================================================
  三、已确认的 Bug（4 个）
================================================================================

🔴 Bug 1（严重）：编辑物料 API 可绕过状态流转
----------------------------------------------------------------
位置：app.py 第 835 行  api_edit_material()

问题描述：
  编辑物料的 API 直接接受 status 参数并写入数据库，没有任何校验。
  这意味着：
  - 售后中的物料可以直接改为"在库"，售后工单变成孤儿记录
  - 故障中的物料可以直接改为"已出库"，跳过修复流程
  - 完全绕过了状态机设计

代码片段：
  db.execute(
      "UPDATE materials SET hw_version=?, sw_version=?, ... status=?, category_id=? WHERE sn=?",
      (..., data.get('status', material['status']), cat_id, sn)
  )

修复建议：
  在编辑 API 中移除 status 字段的直接更新，或者添加状态流转合法性校验。


🟡 Bug 2（中等）：删除物料没有状态检查
----------------------------------------------------------------
位置：app.py 第 1066-1077 行  api_delete_material()
      app.py 第 1080-1099 行  api_batch_delete()

问题描述：
  其他操作（出库、入库、售后、故障）都有状态检查，但删除物料完全没有。
  可以直接删除"售后中"或"故障中"的物料，级联清除所有关联记录。

对比：
  出库(第862行): if mat['status'] == '已出库': return error
                    if mat['status'] == '售后中': return error
                    if mat['status'] == '故障中': return error
  入库(第960行): if material['status'] == '售后中': return error
                    if material['status'] == '故障中': return error
  删除(第1066行): 无任何状态检查！


🟡 Bug 3（中等）：故障创建不检查已出库状态
----------------------------------------------------------------
位置：app.py 第 1021-1042 行  api_fault()

问题描述：
  可以对"已出库"的物料直接创建故障记录。
  虽然 previous_status 会保存并在修复后正确恢复，
  但物料物理上已在客户手中，系统中却是"故障中"状态，
  缺乏业务合理性。


🟢 Bug 4（低）：品类 ID 无有效性校验
----------------------------------------------------------------
位置：app.py 第 728-732 行

问题描述：
  添加/编辑物料时，category_id 只做了 int() 类型转换，
  没有检查该 ID 是否真实存在于 categories 表中。
  传入 category_id=99999 会被接受。

================================================================================
  四、逻辑设计问题（4 个）
================================================================================

1. 售后完成强制自动出库
  - app.py 第 1007-1016 行
  - 售后完成后自动创建"售后返客户"出库记录，物料变"已出库"
  - 但修好的设备不一定都要返给客户
  - 前端缺少"修好后是否返还客户"的选择

2. 一维状态机无法表达组合状态
  - 已出库的设备也可能被客户报故障（"已出库+故障中"）
  - 已出库的设备也可能走售后（"已出库+售后中"）
  - 当前只能有一个状态值

3. 删除出库记录时的状态恢复不严谨
  - app.py 第 926-929 行
  - 只检查剩余出库记录是否为 0
  - 但如果删除的不是最后一条出库记录，逻辑上有歧义

4. 批量出库不是原子操作
  - app.py 第 1313-1324 行
  - 用 for 循环逐个执行，无事务包裹
  - 第3个SN失败时，前2个已经出库成功了

  八、技术栈
================================================================================

  后端：      Python Flask

  数据表：
    categories          — 二级品类管理
    materials           — 物料主表
    outbound_records    — 出库记录
    after_sales_records — 售后工单
    fault_records       — 故障记录
    version_changes     — 版本变更历史

  物料状态流转：
    在库 → 已出库 / 售后中 / 故障中
                ↑        ↑
                └────────┘  (修复/完成后恢复)
